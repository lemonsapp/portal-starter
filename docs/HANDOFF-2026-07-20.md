# HANDOFF — 2026-07-20 · Favicon del shop en mobile (override de la DB)

> Continúa la saga de favicons (`HANDOFF-2026-07-19-b/-c.md`). El cliente
> reportó que en mobile el **shop** seguía mostrando el favicon de Lemons.

## 1. Diagnóstico

Se verificó contra prod (md5 contra el repo) que **todos los estáticos ya
eran la H** después del deploy de ayer:

- `hgrowshop.com/portal/icons/icon.svg`, `icon-192.png` → idénticos al repo ✔
- `hgrowshop.com/icons/icon-192.png`, `/favicon.ico`, `/portal/manifest.json` → ✔

Lo que quedaba mal era el **override runtime de la DB de prod**
(`GET api.hgrowshop.com/api/config/public`):

```
"favicon_url": "https://portal-starter.vercel.app/portal/icons/holistic-logo.svg"
"logo_url":    "https://portal-starter.vercel.app/portal/icons/holistic-logo.svg"
```

Dos problemas: (a) dominio del deploy viejo (`portal-starter.vercel.app`),
(b) `holistic-logo.svg` es la **H negra sobre transparente** — como favicon
desaparece en tabs oscuras. `useBranding()` pisaba el `<link rel=icon>` con
eso en cada carga del portal/shop. Era la trampa ya anticipada en el
handoff 2026-07-19-b ("si el wizard guardó un favicon_url viejo, pisa el
default") — confirmada.

## 2. Qué se hizo (`c8907d9`)

Normalización de valores legacy **al leer** (no hay acceso a la DB de prod
desde acá; el dato queda sucio en la DB pero ya no se sirve sucio):

- **`client/src/lib/branding.js`** — `normalizeBranding()` sobre la
  respuesta remota: URLs absolutas a `portal-starter.vercel.app` →
  relativas; `holistic-logo.svg` como favicon → default
  (`/portal/icons/icon.svg`, la H sobre cuadrado negro). Bonus fixes:
  - Si `favicon_url` == default, ya **no se toca el DOM** (antes pisaba el
    link SVG en cada carga sin necesidad).
  - Un favicon custom real ahora reemplaza **todos** los `link[rel=icon]`:
    antes solo pisaba el primero y quedaba el PNG default al lado, que
    mobile Chrome elige por tamaño → el custom nunca se veía en mobile.
- **`server/lib/configStore.js`** — `normalizeBrandingUrl()` espejo, dentro
  de `getConfig()`: cubre `/api/config/public`, `htmlBranding` y emails.
  Exportado con los helpers de test.

Verificación: `node -c` server OK, `client && npm run build` OK, smoke test
de la normalización (7 casos: legacy → icon.svg, favicon custom de
Cloudinary pasa intacto, keys no-URL intactas).

## 3. Deploy

- **Vercel (client)**: auto-deploy al pushear → el fix del favicon en
  mobile queda vivo solo.
- **Render (server)**: auto-deploy sigue **OFF** → hay que deployar a mano
  para que la API sirva el favicon_url normalizado. No es urgente: el fix
  del client alcanza para lo que ve el usuario; el del server cubre emails
  y el manifest dinámico.

## 4. Post-deploy / si el cliente "sigue viendo el limón"

1. Los favicons se cachean agresivo: hard-refresh o incógnito antes de
   debuggear. En iOS, si el sitio estaba agregado a inicio, borrar y
   re-agregar.
2. Limpieza opcional de raíz: re-guardar branding desde el wizard admin
   (o borrar `branding.favicon_url`/`logo_url` de `app_config`) para que
   la DB quede limpia y no dependa de la normalización.
3. Google (favicon en resultados de búsqueda) tarda días en refrescar.
