## 1. 💳 MercadoPago conectado EN PRODUCCIÓN (hito)

El código de Checkout Pro existía desde F2 pero nunca se había conectado
(0 filas `mercadopago.*` en `app_config`). Hoy se completó todo el circuito
con el usuario paso a paso:

### Bugs que hubieran roto el flujo el día 1 (arreglados, `e728628`)

1. **`notification_url` apuntaba al host equivocado**: se armaba con
   `APP_URL` (sitio en Vercel) pero el sitio NO tiene rewrite `/api/*` →
   Render. MP hubiera notificado a un 404 y toda orden quedaba
   `pending_payment` para siempre. Ahora usa
   `API_PUBLIC_URL || RENDER_EXTERNAL_URL` (automática en Render) con
   fallback a `APP_URL` + `console.warn`. `back_urls` siguen con `APP_URL`
   (son páginas del sitio). `API_PUBLIC_URL` documentada en
   `server/.env.example`.
2. **La guía del wizard mostraba la URL de webhook con
   `window.location.origin`** (mismo bug). Ahora muestra `${API}/api/webhooks/…`
   con el webhook_secret tipeado interpolado.

### "Probar conexión" para MP (`e728628` + `acfe690`)

Nuevo provider `mercadopago` en `POST /api/admin/config/test/:provider`:
pega a `GET /users/me`, devuelve cuenta + site_id + si es sandbox.
**Ojo formato nuevo**: MP ya no usa prefijo `TEST-` para credenciales de
prueba de apps nuevas — emite `APP_USR-…` del *usuario de prueba*; se
detecta por tag `test_user` / nickname `TESTUSER*` (`acfe690`).

### Proceso completado con el usuario

- App "Holistic Shop" (Checkout Pro) creada en la cuenta MP del cliente.
- Credenciales de prueba → compra de prueba end-to-end **verificada**:
  orden `HLS-XSRW-7GJC` pasó a `paid` SOLA vía webhook (mp_payment_id
  `167312452729`). Para pagar en sandbox hizo falta un **comprador de
  prueba** (error "una de las partes es de prueba" si pagás con cuenta real).
- Swap a **credenciales de producción** → "Probar conexión" OK.
- El webhook NO se configuró en el panel de MP: no hace falta —
  `notification_url` va por preferencia en cada checkout.
- ⚠️ Pendiente de limpieza: marcar `HLS-XSRW-7GJC` como Cancelada desde el
  admin (orden de prueba, quedó "Pagada" y ensucia stats).

## 2. 🏦 Pago por transferencia bancaria (feature nueva, `cd2964d`)

Pedido del cliente mid-sesión. Flujo completo:

1. Checkout ofrece **MercadoPago o Transferencia** (selector nuevo; la
   opción aparece sólo si `app_config → shop.transfer_details` tiene datos).
2. Transferencia → orden `pending_payment` sin preferencia MP; la success
   page muestra los **datos bancarios** (Banco Galicia / CBU / alias,
   seed one-shot `seed-transfer-details`; editable en `/setup-admin` paso
   Shop) + monto + copiar + **subir comprobante** (foto/captura →
   Cloudinary `portal-receipts`).
3. Admin ve 🏦 en Pedidos, abre el detalle con el **comprobante embebido**
   y aprueba con el botón "Pagado" de siempre (dispara email de
   confirmación). Broadcast in-app al admin cuando entra un comprobante.

Detalles técnicos:
- `orders.payment_method` (`CHECK mercadopago|transfer`) +
  `orders.transfer_receipt_url`.
- `GET /api/shop/payment-methods` (público) le dice al checkout qué ofrecer.
- Endpoint público de comprobantes con hardening post-review:
  `uploadLimiter` 20/h/IP, allow-list JPG/PNG/WebP/HEIC (sin SVG — XSS),
  guards 404/409, re-subir reemplaza y borra el asset viejo, 503 amable si
  Cloudinary no está configurado.
- Review del code-reviewer dejó 2 LOW conocidos: conexión de pool retenida
  post-COMMIT (patrón pre-existente de todo el checkout) y los datos
  bancarios del cliente viven en el seed de `migrate()` — **cuando
  portal-starter se re-use como boilerplate hay que pelar este seed junto
  con todos los seeds Holistic** (deuda ya conocida del repo).
