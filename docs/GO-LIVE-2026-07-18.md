## 1. Pre-flight (hacer ANTES de tocar DNS)

### 1.1 Env vars en Render (API) — CRÍTICO

El endurecimiento de seguridad hace **obligatorias** algunas de estas. Si falta `JWT_SECRET`, el server **no arranca** (fail-closed, a propósito). Si falta `APP_URL`, el checkout usa fallback localhost y rompe los links de pago de MercadoPago.

| Var | Valor | Notas |
|-----|-------|-------|
| `DATABASE_URL` | connection string de Neon (`...sslmode=require`) | ya seteada si la API ya corría |
| `JWT_SECRET` | `openssl rand -hex 32` | **obligatorio** — sin esto la API aborta el boot |
| `MASTER_KEY` | `openssl rand -hex 32` | **NO cambiar** si ya está: rota-la y hay que re-pegar todas las API keys del wizard |
| `APP_URL` | `https://hgrowshop.com` | **obligatorio ahora** — de acá salen back_urls y el fallback del webhook de MP |
| `NODE_ENV` | `production` | activa CSP estricta + HSTS |
| `WEBAUTHN_RP_ID` | `hgrowshop.com` | apex, sin `https://` ni puerto. Si no se setea, se deriva de `APP_URL` (queda igual) |
| `WEBAUTHN_ORIGIN` | `https://hgrowshop.com` | opcional; acepta lista con coma si sumás `www` |
| `API_PUBLIC_URL` | (no setear en Render) | Render usa `RENDER_EXTERNAL_URL` solo |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | opcional | alertas internas |

> Generar secrets (si hacen falta nuevos):
> ```bash
> node -e "console.log('JWT_SECRET=' + require('crypto').randomBytes(32).toString('hex'))"
> node -e "console.log('MASTER_KEY=' + require('crypto').randomBytes(32).toString('hex'))"
> ```

### 1.2 Env vars en Vercel (frontend)

| Var | Valor |
|-----|-------|
| `VITE_API_URL` | `https://api.hgrowshop.com` |

Después de setearla → **redeploy** en Vercel (Vite hornea la var en build; un cambio de env NO aplica hasta re-buildear).

### 1.3 Confirmar que la API responde (con su dominio o el default de Render)

```bash
curl -s https://<render-url-o-api.hgrowshop.com>/health   # {"ok":true}
```

Si `/health` no responde: revisar en Render los logs de boot. El caso más probable ahora es `JWT_SECRET` faltante → el proceso sale con "JWT_SECRET no está seteado. Abortando."

## 2. DNS — el cambio de mañana (Hostinger → Cloudflare)

El dominio está registrado en **Hostinger**. Decisión 2026-07-18: la zona DNS se
gestiona en **Cloudflare** (free plan) — DNS más rápido de propagar, CNAME
flattening en el apex, y panel independiente del hosting viejo.

### 2.0 Backup ANTES de tocar nada

En Hostinger → Dominios → hgrowshop.com → DNS: **screenshot + copia de TODOS los
records actuales** (A, CNAME, MX, TXT/SPF/DKIM). Es el rollback y la fuente de los
records de mail que hay que preservar.

### 2.1 Alta en Cloudflare

1. dash.cloudflare.com → **Add a site** → `hgrowshop.com` → plan **Free**.
2. Cloudflare escanea e importa los records existentes. **Verificar contra el
   backup** que estén los MX y TXT (SPF/DKIM de Resend y del mail de
   `contacto@hgrowshop.com`) — el scan a veces se come TXT.
3. Cloudflare da 2 nameservers (ej: `ana.ns.cloudflare.com` / `bob.ns.cloudflare.com`).
4. En **Hostinger** → Dominios → hgrowshop.com → Nameservers → **Change nameservers**
   → pegar los 2 de Cloudflare. (Propagación de NS: minutos a ~24h, típico <1h.)

### 2.2 Records en Cloudflare

| Tipo | Nombre | Contenido | Proxy |
|------|--------|-----------|-------|
| CNAME | `hgrowshop.com` (apex, flattening automático) | `cname.vercel-dns.com` | **DNS only (nube gris)** |
| CNAME | `www` | `cname.vercel-dns.com` | **DNS only** |
| CNAME | `api` | `<servicio>.onrender.com` | **DNS only** |
| MX/TXT | (los del backup: mail + SPF/DKIM Resend) | sin cambios | — |

> **Proxy gris a propósito**: Vercel y Render traen su propio CDN + TLS. Con la
> nube naranja hay que configurar SSL "Full (strict)" y desactivar features que
> rompen (Rocket Loader, Always Online) — no aporta nada hoy y complica la
> validación de certs. Si más adelante queremos WAF/cache de Cloudflare, se
> prende la nube naranja **después** de que todo funcione, con SSL/TLS en
> **Full (strict)** (nunca "Flexible": loop de redirects).
>
> En Cloudflare → SSL/TLS: setear modo **Full (strict)** ya mismo aunque el
> proxy esté gris — así queda correcto si alguien prende la nube después.

Luego:
1. **Vercel → Settings → Domains → Add `hgrowshop.com`** (y `www.hgrowshop.com`) en el proyecto de ESTE repo. Vercel valida el dominio y emite el cert TLS automático.
   - Si `hgrowshop.com` ya figura en Vercel apuntando al proyecto WordPress-proxy, hay que **removerlo de ese proyecto y agregarlo al del portal** (reasignación de dominio dentro de Vercel — puede que no requiera cambiar los records si ya están en Vercel).
2. **Render → Settings → Custom Domain → `api.hgrowshop.com`**. Emite cert automático.
3. Confirmar `APP_URL=https://hgrowshop.com` y `VITE_API_URL=https://api.hgrowshop.com` (paso 1) y **redeploy de ambos** (Render + Vercel).

> Propagación DNS: minutos a ~1h. Verificar con `dig hgrowshop.com +short` y `dig api.hgrowshop.com +short`.

```bash
PORTAL=https://hgrowshop.com
```

- [ ] Login / registro funciona; el mail de verificación llega (Resend)
- [ ] **Reset de contraseña**: pedirlo, llega el mail, el link resetea (token ahora es criptográfico; el endpoint tiene rate-limit)

- [ ] Comprar monedas y pagar un pedido con monedas → saldo baja, no queda negativo

## 4. Rollback (si algo sale mal)

El WordPress viejo sigue intacto — el cutover es sólo de DNS/dominio:
1. **Opción rápida**: en Cloudflare, revertir los records de `hgrowshop.com` y `www` a los valores del backup de Hostinger (§2.0). Propagación en minutos (TTL de Cloudflare es bajo).
2. **Opción nuclear**: en Hostinger, volver los nameservers a los de Hostinger — restaura la zona vieja completa. Más lento (propagación de NS).

> **IMPORTANTE**: el backup de records del §2.0 es lo que hace posible el rollback en segundos. No saltearlo.
